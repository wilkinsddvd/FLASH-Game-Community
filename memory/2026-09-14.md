## 02:19 用户要求「继续备份」→ 已恢复备份并跑通大部分

### 真正的根因（推翻上一节的猜测）
- 缺的 143,607 个文件 = `~/Desktop` 里 **iCloud 已驱逐(dataless) 的文件**，数量完全吻合（`find ~/Desktop -flags +dataless`）。9/13 那次复制读不到它们，所以静默跳过（不是工具 bug）。
- `~/Desktop` 本身就是 iCloud 桌面：`~/Library/Mobile Documents/com~apple~CloudDocs/Desktop -> /Users/linhao_wang/Desktop`，`optimize-storage=1`。
- 读 dataless 文件立即 `EDEADLK / errno 11`（`Resource deadlock avoided`）；`read` 工具报 `Unknown system error -11`。sandbox 和 gateway host 都一样 → 不是 OpenClaw 沙箱问题。
- FileProvider 卡死：`fileproviderctl dump` 显示大量 `fetchContentsForItemWithID ... (no timeout), no progress`。
- 可用手段：`brctl download <path>`（请求下载）、`brctl quota`（剩 ~2.8GB，**不是配额满**）、`brctl status`、`fileproviderctl dump`。
- iCloud 守护进程都是**用户态**（cloudd/bird/fileproviderd 跑在 linhao_wang 下）→ 不用 sudo 就能 `killall` 复位。
- **Mac 在用电池（41%，未插电）**：macOS 会限制 iCloud 后台传输 → 下载速度被卡在 ~1 文件/秒（插电时曾出现 ~11/秒 的爆发）。建议用户插电源。
- 之前会话的 `killall cloudd`（每5轮）+ 我重启 bird/fileproviderd/cloudd 后，曾经解锁过一批（~6.5k 文件），但不稳定。

### 已完成（本次）
- 恢复备份：先用 `/tmp/backup2.py`（旧脚本，跑 120 轮后停在 77k 待补），但它的 `xargs brctl` 会被单个 hang 的 brctl 拖死、复制用 signal.alarm 对阻塞 read 无效。
- 新脚本 **`/tmp/backup3.py`**（推荐后续用它）：
  - 复制用 `os.fork()` 子进程 + 父进程硬超时 SIGKILL，杜绝卡死；
  - brctl 用 `perl -e 'alarm shift; exec @ARGV' 12` 包一层超时（本机没有 timeout/gtimeout）；
  - 每 N 轮 `killall cloudd bird fileproviderd` 复位；**绝不删除任何文件**（别名占位冲突就跳过）。
  - 环境变量：`BK3_ROUNDS / BK3_QUIET / BK3_DAEMON_EVERY / BK3_BATCH / BK3_COPY_BUDGET`；日志 `/tmp/backup3.log`。
  - 启动方式：`nohup python3 /tmp/backup3.py >> /tmp/backup3.out 2>&1 &`（或走 exec 后台会话）。
- **核对结果（按大小逐文件比对）**：除 `openclaw-backup/` 外，全部 100% 已备份 ✅ —— `dev` 14,722/14,722、`obsidian` 108/108、`截图` 30/30、所有顶层文件（1.pdf、RAAS模式编制.zip、covers、openclaw备份、openclaw.json.md、3 张截屏…）。

# 功能测试 + 性能测试方案（2026-10-20）

> 目标：上线后持续保证网页端**功能正确**、**交互稳定**、**加载与运行时性能可接受**。
> 本文是方案，不代表已经全部实现；按阶段落地。

---

## 0. 现状与基线（先有数据，再定标准）

### 0.1 已有测试资产

| 类型 | 现有 |
|---|---|
| 数据/算法自检 | `test-raas-solver.mjs`、`test-roster-groups.mjs`、`test-vehicle-stats.mjs`、`test-fire-control.mjs` |
| UI 无头点验 | `verify-ui-cdp.mjs`、`verify-ui-overlay.mjs`、`verify-ui-vehicles.mjs` |
| 后端压测 | `FLASH_END_PRO/tests/load/locustfile.py` + `prepare_tokens.py` |
| 构建自检 | `npm run build` |

缺口：没有统一的 API 功能测试、没有完整 E2E 用例集、没有前端性能门禁、没有压测阈值与报告归档。

### 0.2 当前构建体积（生产构建实测）

| 资源 | 原始 | gzip |
|---|---:|---:|
| `index-*.js`（主包，含 Element Plus） | 1.1 MB | **356 KB** |
| `index-*.css` | 359 KB | 50 KB |
| `raas-data-*.js` | 261 KB | 48 KB |
| `factions-*.js` | 247 KB | 20 KB |
| `invasion-data-*.js` | 107 KB | 23 KB |
| `SquadVehiclesPage-*.js` | 94 KB | 13 KB |

静态资源总量：`dist` 约 114 MB，其中 `squad-assets/raas` 78 MB、`vehicles` 17 MB、`heightmaps` 12 MB、`contours` 2.1 MB。

### 0.3 已发现的性能隐患

1. **主包偏大**：初始 JS gzip 356 KB，Element Plus 全量进入主包；移动端 LCP 有风险。
2. **`/squad-assets/` 没有长缓存**：nginx 只给 `/assets/` 配了 30 天缓存；高程 `.bin`、等高线 `.svg`、地图/载具图片都没有显式 `Cache-Control`，会重复下载。
3. **高程 `.bin` 未压缩**：488 KB/图，nginx 默认 gzip 类型通常不包含 `application/octet-stream`。
4. **地图页资源重**：RAAS 底图/高清图按需加载，但首次进入某地图仍可能拉多张 webp。
5. **等高线 SVG 最大约 154 KB**（Lashkar），可 gzip/预压缩。

> 方案会把“先测基线 → 再优化 → 回归门禁”分开，避免只凭感觉优化。

### 2.2 公共用例

- 路由：全部一级/二级路由 200；未知路由 404 或回首页策略符合预期
- 导航：9 项、顺序、移动端抽屉、当前项高亮
- 响应式：390 / 768 / 1440 三档无横向溢出
- 控制台：无 `error`、无 Vue warning
- 链接：站内链接无 404；外链带 `noopener`
- 空态/加载态/错误态：接口失败、空列表、图片失败回退

### 2.4 API 功能用例

- 认证：注册/登录/刷新/退出；验证码错误；token 过期
- Banner：公开列表只返回 `status=1`；后台 CRUD；上传合法/非法类型/超大；非管理员 403
- 编制：`/api/squad/public` enabled + 17 阵营/80 编制 + 关键字段
- 留言板：提交/审核/展示；空内容/超长；未登录 401

- 错误契约：422 字段错误、404、429 限流
- OpenAPI：关键路径存在（`/api/admin/banners/upload` 等）

### 2.5 功能验收标准

- P0 用例 **100% 通过**
- 0 控制台 error / Vue warning

- 数据计数断言全部命中
- 关键用户路径（浏览→登录→留言→后台审核）可走通

## 3. 性能测试

### 3.1 前端加载性能

**工具**：Lighthouse CI（`@lhci/cli` 或 `npx lighthouse`）+ 自写 Web Vitals 采集（PerformanceObserver）。

**页面**：

- 首页
- 载具阵营选择页 / 单阵营页
- 点位模式页 / 地图列表 / Invasion 图层
- 火控计算器（含高程与等高线加载）

**指标与暂定预算（移动端 4G/CPU 4× 模拟）**：

| 指标 | 目标 |
|---|---|
| LCP | < 2.5 s |
| CLS | < 0.1 |
| INP | < 200 ms |
| TBT | < 300 ms |
| 首屏 JS（gzip） | < 300 KB（当前 356 KB，先优化再收紧） |
| 首屏 CSS（gzip） | < 60 KB |
| 单路由 chunk（gzip） | < 150 KB |
| 首屏请求数 | < 25 |
| 高程/等高线 | 懒加载，不进入首屏 |

**交互性能**：

- 地图滚轮缩放/拖动：FPS ≥ 50，长任务 < 200 ms
- 点位确认：点击到 UI 更新 < 100 ms
- 火控输入坐标到结果更新 < 100 ms
- 载具浮层出现 < 150 ms
- 等高线开关 < 200 ms

### 3.2 后端/API 压测

**工具**：现有 Locust 扩展。

**场景**：

1. 匿名浏览：banner/articles/videos/squad/message-board/likes
2. 登录态：未读轮询、个人资料、留言提交
3. 验证码：CPU 敏感
4. 写路径：留言/反馈（测试库，跑完清理）
5. 新增：Banner 上传（小文件）可单独低并发压，避免磁盘写爆

**步骤**：

- 基线：1 并发 1 分钟，记录 p50/p95/p99
- 阶梯：10 / 50 / 100 / 200 并发，每档 3 分钟，找 RPS 拐点
- 长稳：拐点 60–70% 并发跑 30 分钟，观察内存/连接数泄漏
- 同步观测：MySQL `Threads_connected`/慢查询、Redis `info stats`、`docker stats`

**暂定阈值（以 staging 实测校准）**：

| 指标 | 目标 |
|---|---|
| 读接口 p95 | < 300 ms |
| 读接口 p99 | < 800 ms |
| 100 并发错误率 | < 0.1% |
| 5xx | 0 |
| 30 分钟内存增长 | < 10% |

### 3.3 静态资源/nginx 压测

**工具**：`wrk` 或 `hey`（比 Locust 更适合静态吞吐）。

**对象**：

- `/assets/index-*.js`
- `/squad-assets/heightmaps/mutaha.bin`（488 KB）
- `/squad-assets/contours/lashkar.svg`（154 KB）
- `/squad-assets/raas/maps/mutaha.webp`

**关注**：

- TTFB、吞吐、并发下的错误率
- 缓存头：`/assets/` 已有 30 天；**`/squad-assets/` 需要补 `Cache-Control`**
- gzip/brotli：SVG/JSON 必须压缩；`.bin` 评估预压缩或 Brotli
- 304/命中率

### 3.4 生产环境只读巡检

- 仅单用户/低频率：首页、点位、载具、火控 HTTP 200
- Lighthouse 单次跑生产首页（不并发、不写数据）
- 严禁对生产做阶梯/长稳压测（现有 README 已有此约束）

## 4. 测试环境与数据

| 环境 | 用途 | 约束 |
|---|---|---|
| 本地 Docker Compose | 功能/API/压测开发 | MySQL 3307 + Redis；独立库 |
| Staging（建议） | 性能基线/长稳 | 与生产同镜像、独立 DB/Redis/上传目录 |
| 生产 | 只读巡检 + Lighthouse 单次 | **不压测、不写数据** |

**数据隔离**：

- API/E2E 使用独立测试库；每次跑前 `reset_db` 或事务回滚
- Locust 测试用户 `loadtest_*`；留言/反馈记录跑完清理
- 图片上传测试使用临时目录/测试库，不写生产 `uploads`

## 7. 风险与待确认

| 风险 | 应对 |
|---|---|
| 生产压测风险 | 只读巡检；压测只在本地/staging |
| 测试数据污染 | 独立库 + 跑完清理 |
| 验证码/bcrypt 路径压不到 | 测试环境加开关；生产不压 |
| 地图交互 flaky | 固定视口、冻结动画、等待网络空闲 |
| 新功能多为静态 | 前端性能是重点，后端压测覆盖增量接口即可 |
| 外部图片/Wiki 不可用 | 运行时已本地化；测试不依赖外网 |

**需要你确认：**

1. 是否有 staging 环境？没有的话，是否同意在服务器上起一套 3001/8001 的 staging 容器（独立库）？
2. 性能目标以“100 并发 / p95 300ms”作为暂定基线，还是按你预期的在线人数定？
3. E2E 是否接受引入 Playwright（`@playwright/test`）？还是只沿用现有零依赖 CDP 脚本？
4. 是否需要接入 CI（GitHub Actions），还是本地一键脚本 + 人工跑即可？
5. 浏览器范围：只测 Chrome/Chromium，还是加 Safari/移动端真机？

# FLASH 安全限流方案（防 DDoS / 防撞库 / 防批量注册）

> 范围：`/api/auth/*` 下的**用户名注册**与**登录**（含邮箱验证码），目标是「防暴力破解 + 防批量刷号 + 抗 CC 打穿」，同时不影响正常用户。
> 状态：**方案待确认**，确认后再写代码。

---

## 一、现状盘点

**已经有的防护**
| 位置 | 机制 |
|---|---|
| `core/admin_auth.py` | 管理员口令防爆破：IP 维度，5 次失败锁定 30 分钟（Redis） |
| `api/email.py` | 邮箱验证码：同邮箱 60s 内不可重发 |
| `api/deps.py` | 账号封禁 `banned_until` 全局拦截 |
| `db/db.py` | 连接池（默认） |

**缺口（本次要补）**
1. **用户名注册完全无限制** → 可被脚本无限刷号。
2. **用户名登录无失败计数** → 可无限撞库（目前只有口令注册接口有防爆破）。
3. 无非 auth 接口的全局 QPS 保护 → 任何接口都能被打。
4. 接入层（nginx）没有限流 → 攻击流量直接打到 Python 进程。

## 二、分层方案

### L1 接入层：nginx 限流（收益最大、零代码风险）

改 `frontend/nginx.conf`，按 IP 限速，把绝大部分洪水挡在 Python 之前：

```nginx
# http 块内定义
limit_req_zone  $binary_remote_addr zone=auth_zone:10m rate=10r/m;
limit_req_zone  $binary_remote_addr zone=api_zone:10m  rate=120r/m;
limit_conn_zone $binary_remote_addr zone=conn_zone:10m;

# auth 相关接口：严格限流
location ~ ^/api/auth/(login|register|admin/register|email/send-code|email/login|admin/send-code) {
    limit_req  zone=auth_zone burst=5 nodelay;
    limit_conn conn_zone 10;
    proxy_pass http://backend:8000;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}

# 其余 API：宽松限流
location /api/ {
    limit_req  zone=api_zone burst=40 nodelay;
    limit_conn conn_zone 30;
    proxy_pass http://backend:8000;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}

client_max_body_size 6m;   # 防超大 body 打内存
```

**配套（部署层，备案完成后）**
- 只暴露 443，后端 8000 不直接对公网（安全组只放行反代/负载均衡）。
- 上云 CDN / 云 WAF 的 CC 防护（阿里云/腾讯云基础 DDoS 防护默认可用）。
- 可选：`fail2ban` 按 nginx 日志自动拉黑高频 IP。

### L2 应用层：Redis 限流（本次写代码的部分）

新增 `core/ratelimit.py`，提供两类能力：

1. **固定窗口计数**（`INCR` + `EXPIRE`，原子、够用、成本低）
   键：`rl:{scope}:{identifier}:{window}`
2. **FastAPI 依赖** `rate_limit(scope, limit, window, by=...)`，超限统一抛 `429` 并带 `Retry-After` 头。

`identifier` 支持三种维度（可组合）：
- `ip`：`X-Forwarded-For` 第一个 / `request.client.host`
- `ip_user`：`ip + username`（用于登录失败锁定，**避免攻击者恶意锁别人账号**）
- `user`：仅用户名（用于告警阈值，不用来锁定）

**策略表（阈值全部放进 `core/config.py`，便于随时调）**

| 接口 | 维度 | 阈值 | 触发结果 |
|---|---|---|---|
| `POST /api/auth/login` | IP | 20 次 / 分钟 | 429 + `Retry-After: 60` |
| `POST /api/auth/login` | IP+用户名 **失败** | 5 次 / 15 分钟 | 该组合锁 15 分钟（429） |
| `POST /api/auth/login` | 用户名 **失败** | 30 次 / 小时 | 仅记审计 + 告警（**不锁**，防误伤） |
| `POST /api/auth/register` | IP | 5 次 / 分钟；20 次 / 小时；10 次 / 天 | 429 |
| `POST /api/auth/email/send-code` | IP | 10 次 / 小时（叠加已有 60s/邮箱） | 429 |
| `POST /api/auth/admin/register` | IP | 3 次 / 分钟（叠加已有口令防爆破） | 429 |
| 全部 `/api/*` | IP | 300 次 / 分钟 | 429（兜底） |

**其它细节**
- 登录**成功**时清空该 `ip+用户名` 的失败计数。
- 失败文案统一为「尝试过于频繁，请 X 分钟后再试」，不暴露"用户名是否存在"。
- Redis 不可用时 **fail-open（放行 + 记日志）**，避免 Redis 抖动把登录整体打挂 —— 见待确认项 2。
- 每次触发限流写一条审计日志（时间/IP/scope），便于识别攻击。

### L3 服务韧性
- uvicorn 启动加 `--limit-concurrency 200`（超并发直接 503，保住进程）。
- SQLAlchemy 连接池上限保护（`pool_size` / `max_overflow`）+ MySQL `max_connections` 对齐。
- 慢接口（`/api/squad/public` 返回 ~300KB）可加缓存，减少被打时的资源消耗。

### L4 可选增强（视攻击强度再上）
- **图形验证码**：注册必填；登录失败 1 次后出现（最有效的人机区分手段）。
- 新注册账号在绑定邮箱/微信前，限制发帖/留言等写操作（降低刷号收益）。
- IP 段级聚合（/24）限流，对付大量肉鸡。

**先说结论：**

- 网页端**没有横向溢出问题**（已实测 10 条路由 × 3 档视口），真正要修的是**触控目标过小、移动端信息层级、地图手势和结果区**。

## 2. 需求 ①：网页端移动适配优化

### 2.1 目标

- 360–430px 主流手机、768px 平板、桌面三档都“能顺手用”，而不是“能看不炸”。
- 关键路径（首页 → 点位 → 火控 → 认证 → 关于）全部单手可完成。
- 移动端首屏 JS gzip ≤ 300KB，4G 中端机 LCP ≤ 2.5s。

### 2.2 改动方案

**A. 设计口径（全局）**

| 项 | 口径 |
|---|---|
| 断点 | xs < 480；sm 480–767；md 768–1023；lg ≥ 1024（沿用现有 480/640/768，补 1024） |
| 触控目标 | 主要可点元素 ≥ 44×44；次要 chip ≥ 40×40；纯文字链接可例外但要加 8px 内边距 |
| 输入框 | 移动端 `font-size: 16px`（防 iOS 自动放大）；坐标输入 `inputmode="text"`、`enterkeyhint="done"` |
| 安全区 | header/footer/底部抽屉统一 `env(safe-area-inset-*)`；地图高度用 `100dvh` 不用 `100vh` |
| hover | 所有 hover 才出现的信息，在 `@media (hover: none)` 下改为常显或点击展开 |
| 动效 | 尊重 `prefers-reduced-motion`；移动端关闭非必要过渡 |

**B. 逐页改动**

| 页面 | 改动 |
|---|---|
| 全局 `style.css` | 统一 `.el-button`/`.mini`/`input`/`select` 最小高度 44（移动端）；header 抽屉加遮罩、打开时锁 body 滚动、ESC/点遮罩/路由切换关闭 |
| `HomePage` | Banner 移动端改 `scroll-snap` 横滑（现为左右栏降级）；卡片网格 1 列；图片 `loading="lazy" decoding="async"` |
| `SquadPage` | 筛选 chip 高度 29 → 40，横向滚动加渐隐提示；搜索框吸顶 |
| `SquadPointsPage` | 模式卡 1 列；说明文字折叠 |
| `SquadRaasPage`（地图列表） | 版本 chip 25 → 40 高；每张地图一张整卡；筛选/搜索吸顶 |
| `SquadRaasLayerPage` | 顶栏按钮 40+；图例/已确认点位改底部抽屉（现在移动端已是 fixed sheet，补齐展开态与安全区）；缩放按钮 44；提示气泡不遮挡候选点 |
| `RaasMap` | 保留现有手势；补：双指缩放时禁用页面滚动（已 `touch-action:none`）、惯性平移、缩放后按钮可用性、`overscroll-behavior: contain` |
| `FireControlPage` | 移动端结果区改**底部 sticky 摘要条**（点击展开完整诸元）；按钮/输入 44 高；武器/弹种用原生 `select` 或底部选择器 |
| `FireControlMap` | 新增 Pointer Events：单指拖拽平移、双指缩放、单击落点、长按放大镜（loupe）；点选时以“十字线 + 放大镜”避免手指遮挡 |
| `CertPage` / 记录表 | ≤640px 表格改卡片列表（题名/分数/时间/结果），避免横向滚动；单选整行可点 |
| `AboutPage` / `Messages` / `Settings` | 表单 label 上置、按钮全宽、列表项 44+ |
| 后台 `admin/*` | **桌面优先**（见下方说明）：≤768px 顶部显示一条提示条“建议在电脑端管理，移动端仅保证可查看”，页面布局不动、表格保留横向滚动，不做移动端卡片化 |

**关于“仅提示、仍以桌面为主”具体是什么意思：**

- **不改后台版式**：表格仍是表格、筛选区仍是原来的排列，不为了手机去卡片化重写。
- **只加一条提示**：≤768px 时页面顶部出现一条提示（可关闭），文案类似“后台管理建议在电脑端操作；移动端仅保证查看，复杂编辑可能不便”。
- **能用但不好用**：手机上能打开、能看列表、能搜索/筛选，但新增/编辑多个字段的表单会很挤，不保证体验。
- **为什么不改**：后台是低频、强操作场景，移动端重排要 2–3 天，收益很低；同样的时间放给点位/火控更值。以后真要移动化，再单独立项（卡片列表 + 底部抽屉表单）。
- **哪些后台页不受影响**：用户端页面（首页/编制/点位/火控/认证/关于/设置）不适用这条，全部按手机体验优化。

**C. 性能**

- Vite `manualChunks` 拆 `vue` / `element-plus` / `squad-data`，首屏不加载点位数据。
- Element Plus 样式改 `importStyle: 'css'` 按需（需回归暗色主题）。
- 地图/高程/等高线继续按需加载；移动端默认不预取高清图。
- nginx：`/squad-assets/` 加 30 天缓存 + `gzip` 覆盖 `.bin/.svg`（上轮遗留项，一起做）。

**D. 测试**

- Selenium 新增 `tests/e2e/test_mobile.py`：3 视口 × 10 路由；断言无横向滚动、主按钮 ≥44、抽屉开合、地图点选、火控输入与结果可见。
- Lighthouse mobile（首页/点位/火控）预算：Performance ≥ 80、LCP ≤ 2.5s、CLS ≤ 0.1、TBT ≤ 300ms。
- 构建体积门禁沿用 `check-bundle-size.mjs`，首屏 JS 预算从 380KB 收紧到 300KB。

### 2.3 验收

- 360/390/430/768 四档，10 条路由 0 横向溢出。
- 所有主操作（导航、筛选、选点、缩放、计算、复制）单手可点，触控目标达标率 100%（白名单除外并注明）。

## 3. 需求 ②：小程序 tab 调整 + 点位推测 / 火控计算器

### 3.1 tabBar 最终形态（合并为一个「战术工具」页）

**可以放一个界面，而且推荐这么做。** 两个功能都是“选地图 → 在地图上点 → 出结果”，共用底图、缩放/平移、点位绘制和资源加载，拆成两个 tab 反而要维护两套地图交互。

```
首页 / 游戏编制 / 战术工具 / 关于        （4 个 tab）
```

「战术工具」页顶部用 segmented control 切换：

```
[ 点位推测 ] [ 火控计算器 ]
```

- 同一张 canvas 底图组件，切换时只换图层/交互模式，不重新加载地图。
- 点位模式：先选 RAAS / Invasion → 地图/版本 → 逐点确认。
- 火控模式：选武器 → 地图点炮位/目标或输入网格 → 出诸元。
- 省下的 tab 位可以先空着；以后要加「攻略 / 我的」随时能加（攻略页已存在，目前从首页进入）。

> 如果坚持要 5 个 tab（点位、火控各一个），也能做，但两页要各自维护 canvas 与手势，代码重复、体验不一致，**不推荐**。

### 3.2 页面结构（主包/分包限制）

> 微信规定两条硬约束：**tabBar 页面必须在主包**；**主包不能引用分包里的组件/数据，分包之间也不能互相引用**。
> 所以「战术工具」这个 tab 页要渲染的内容，必须跟它一起在主包（或改成“tab 落地页 + 分包子页”）。

**推荐方案：单页 + 主包内共享地图组件**

```
miniprogram/
├─ pages/tactical/index           # 主包：segmented + 两个模式容器
├─ components/map-canvas/         # 主包：共用 canvas（底图/缩放/平移/点位/命中）
├─ packageTactical/
│  ├─ points/data.js              # 83 层点位数据（~360KB）
│  ├─ points/solver.js            # 路由/候选求解器（由网页移植）
│  ├─ fire/solver.js              # 弹道/高程/网格
│  └─ fire/weapons.js
└─ app.json                       # tabBar 4 项
```

体积测算：当前主包约 620KB，加点位数据 360KB + 求解器/UI 约 80KB ≈ **1.06MB**，低于 1.5MB 目标、远低于 2MB 硬限。构建后跑 `check-mp-size.mjs`，超 1.5MB 再把数据改为“首次进入时 `wx.request` 拉远端 JSON”的降级方案。

**备选方案（主包超标时）**：`pages/tactical/index` 只做两张入口卡，点位/火控各自放分包页面；代价是多一次点击，且两个页面要共用同一套手势约定（组件仍放主包）。

### 3.3 数据与算法：单一来源 + 一致性测试

现状是网页版 `raas.js` / `fire-control.js` / `squad-grid.js` 都是**纯 ESM 函数**（无 DOM），这是好消息。

做法：

1. 把三个文件整理为“共享核心”（仅做导出收敛，不改算法）。
2. 新增 `scripts/sync-mp-core.mjs`：
   - 从 `frontend/src/utils/{raas,fire-control,squad-grid}.js` 生成小程序可用的 `utils/*-core.js`（去掉 ESM export 语法或统一转 CommonJS/TS 兼容写法）。
   - 生成文件头写 `// AUTO-GENERATED from <path> @ <sha>，勿手改`。
3. 新增 `scripts/test-mp-parity.mjs`：
   - 对 **全部 83 个图层**（39 RAAS + 44 Invasion）比较 `buildRoutes` 的路线集合、点序、深度；
   - 对火控：20 张地图 × 全部武器 × 每图 50 组随机坐标，比较距离/仰角/方位/飞行时间（误差 < 1e-9）。
   - 任何差异 → 非零退出，禁止发版。
4. 数据生成 `scripts/build-mp-points-data.mjs`：从网页数据产出压缩 JSON（预计 RAAS ~250KB、Invasion ~110KB），放 `packagePoints/data/`；不进主包。

### 3.4 地图交互（小程序重写部分）

用 `<canvas type="2d">` 一块画布同时画底图与点位，避免多层 `<image>` 叠加的性能问题。

| 交互 | 行为 |
|---|---|
| 单指拖拽 | 平移；边界回弹 |
| 双指 | 缩放（1×–4×），以两指中心为锚点 |
| 单击点 | 与网页一致：未选且是下一候选 → 选中；已选最后一点 → 取消；已选非最后 → 退回该步；其余提示 |
| 双击 | 1× ↔ 2× 切换 |
| 长按 | 放大镜（可选，P2） |
| 密图 | >120 个后续点时隐藏点名、灰圈细线（沿用网页规则） |
| 性能 | 只重绘视口内点位；标签碰撞检测；`requestAnimationFrame` 合并 |

底图：从 `STATIC_BASE/squad-assets/raas/maps/*.webp` 经 `wx.getImageInfo` 加载（需 downloadFile 合法域名）；高清图按需切换。

### 3.5 火控计算器

| 模块 | 做法 |
|---|---|
| 地图选点 | 复用 canvas 地图；点一下设炮位，再点设目标；支持“重选/清空” |
| 网格输入 | 移植 `squad-grid.js`，支持 `D4-6-3`，错误提示 |
| 武器/弹种 | `picker`，数据来自网页 `weapons.js`（~3KB，可直接进主包/分包） |
| 自动高程 | `wx.request` 拿 `.bin`（arraybuffer）→ `Int16Array` 解码；按地图缓存到 `wx.env.USER_DATA_PATH`，LRU 最多 10 张（约 5MB） |
| 结果 | 仰角（密位/度）、距离、方位、飞行时间、高差、最大射程、低伸/高抛、射界外提示 |
| 等高线 | **v1 不做 SVG**（小程序 `<image>` 不支持 SVG）：构建脚本把 SVG 转 1024px 透明 PNG，远端按需加载；v1.1 再加 |
| 复制 | `wx.setClipboardData` 输出文本诸元 |

### 4.2 Steam 登录（Web）

**流程（OpenID 2.0）**

1. 前端点「Steam 登录」→ `GET /api/auth/oauth/steam/authorize`。
2. 后端生成 `state`（Redis，10 分钟）并 302 到：
   `https://steamcommunity.com/openid/login?openid.mode=checkid_setup&openid.ns=...&openid.return_to=<callback>?state=...&openid.realm=<site>&openid.identity=...identifier_select&openid.claimed_id=...identifier_select`
3. Steam 回跳 `GET /api/auth/oauth/steam/callback?state=...&openid.*`。
4. 后端**必须回源验签**：把全部 `openid.*` 参数改为 `openid.mode=check_authentication` POST 回 Steam，响应含 `is_valid:true` 才可信；禁止只解析 query。
5. 从 `openid.claimed_id` 提取 `https://steamcommunity.com/openid/id/<steamid64>`（17 位数字）作为 `openid`。
6. 查 `user_oauth(provider='steam', openid=steamid64)`：
   - 已绑定 → 登录（检查封禁）；
   - 未绑定且当前已登录 → 绑定到当前账号；
   - 未绑定且未登录 → 自动建号。
7. 生成一次性 `ticket`（Redis 60 秒）→ 302 到前端 `/oauth/callback?ticket=...` → 前端 `POST /api/auth/oauth/exchange` 换 JWT。

**资料**

- `persona` / `avatar` 通过 Steam Web API `ISteamUser/GetPlayerSummaries`（可选，需要 `STEAM_API_KEY`）获取，只存到 `user_oauth.nickname/avatar_url`。
- **不直接覆盖**本站昵称/头像（沿用现有审核口径）；页面显示“Steam：<persona>”。
- Steam 不提供邮箱，账号找回只能靠“已登录会话设置密码/邮箱”，所以必须有设置密码入口。

**账号规则**

- 一个 SteamID 只能绑定一个本站账号；已绑定其他账号 → 拒绝并提示“请先登录原账号解绑”，不做自动合并。
- 首次 Steam 登录自动建号：用户名 `steam_<steamid 后 6 位>`（冲突则加序号），`uid` 走现有发号器，`password_hash=NULL`，`registration_method='steam'`。
- 纯 Steam 账号可在「个人设置」里设置密码/邮箱，之后可用用户名密码登录。
- 解绑保护：没有密码且只剩一个绑定 → 拒绝解绑。

**小程序端说明**

- 小程序**不做 Steam 登录**：OpenID 回跳需要浏览器/web-view，业务域名与审核成本高、体验差。
- 小程序里展示“Steam 绑定请前往网页端”，账号体系仍互通（同一 `users` 表）。

### 4.3 小程序微信登录

- `wx.login()` → `POST /api/auth/wx/login { code }`。
- 后端 `jscode2session` 换 `openid/unionid`；**session_key 不返回、不落库**。
- `provider='wechat_mp'`，`(provider, openid)` 唯一；已存在直接发 JWT，不存在自动建号（`registration_method='wechat_mp'`）。
- unionid 预留给未来 Web 微信登录：同 unionid 的不同 provider 可合并到同一账号。
- 需要绑定网页老账号时：返回 `need_bind + bind_ticket`，前端输入用户名/密码/验证码 → `/api/auth/wx/bind`。
- 小程序 `app.ts` 不做静默登录，改为按需触发（降低隐私与审核风险）。

### 4.4 数据模型（小迁移）

```sql
-- 1) 第三方账号可以没有密码
ALTER TABLE users MODIFY password_hash VARCHAR(128) NULL;

-- 2) 绑定表补“最近登录时间”（安全审计）
ALTER TABLE user_oauth ADD COLUMN last_login_at DATETIME NULL;

-- provider 取值：steam / wechat_mp（后续 wechat_web / qq）
-- unique(provider, openid) 已存在
```

- 迁移写进 `db/db.py::_REQUIRED_COLUMNS`（幂等补列），沿用现有机制，不引入 Alembic。
- `registration_method` 增加 `steam` / `wechat_mp`。
- 密码登录遇到 `password_hash IS NULL` → 返回“该账号仅支持第三方登录，请使用 Steam 登录或先设置密码”。

### 4.5 接口

```
GET  /api/auth/oauth/providers                 # 已启用渠道（Steam 已配置才返回）
GET  /api/auth/oauth/steam/authorize           # → { url, state }
GET  /api/auth/oauth/steam/callback            # 验签 → ticket → 302 前端
POST /api/auth/oauth/exchange                  # { ticket } → token pair
GET  /api/auth/oauth/bindings                  # 当前用户绑定列表（不含 openid）
POST /api/auth/oauth/steam/bind                # 已登录绑定（走同一 authorize，带 bind=1）
POST /api/auth/oauth/steam/unbind              # 解绑（唯一登录方式时拒绝）
POST /api/auth/wx/login                        # 小程序 code 登录
POST /api/auth/wx/bind                         # 小程序绑定老账号
POST /api/auth/set-password                    # 无密码账号设置密码（登录态 + 验证码）
```

- 微信/QQ 的路由保留为 provider 占位：未配置时 `/providers` 不返回，直接访问返回 503。
- JWT 绝不出现在 URL/Referer/日志；`ticket` 一次性、60 秒。

### 4.6 安全清单

- `state` 一次性 + TTL；Steam 必须回源验签；`openid.claimed_id` 必须匹配 Steam 域名与 17 位 ID。
- 登录/绑定限流（IP + provider 维度）；失败日志脱敏。
- 不对外返回 openid/unionid；后台也不展示明文。
- 封禁用户在 OAuth / wx 登录链路同样拦截。
- 绑定/解绑/设置密码写审计日志（复用现有 audit 模块）。
- 设置密码：需登录态 + 图形验证码；如后续要更高安全等级，再加“重新走一次 Steam 验证”。

### 4.7 前端 / 小程序 UI

- `LoginPage.vue`：加「Steam 登录」按钮（Steam 蓝黑配色 + 图标）；微信/QQ 按钮由 `/providers` 控制，未配置不显示。
- 新增 `pages/OauthCallback.vue`：读 ticket → exchange → 存 token → 回跳。
- `ProfileSettings.vue`：账号与绑定区（Steam 已绑定/解绑、设置密码/邮箱）。
- 小程序：`关于` 页加账号区（登录/退出/绑定状态）；需要身份的操作未登录时引导登录。
- 小程序账号区显示“Steam：未绑定（请到网页端绑定）”。
